## Mitchell Hashimoto proposed it on 2026-09-28 to replace screen-scraping of program state

The first gist revision is dated 2026-09-29T01:37Z, and the revision table in that gist dates draft 0.1 to 2026-09-28. The second revision, dated 2026-09-30, adds a terminfo section (§7.1). The gist history shows both revisions. The public announcement is the blog post ["A Terminal Protocol for Program Status (OSC 7501)"](https://mitchellh.com/writing/program-status-osc7501), dated October 6, 2026. The canonical, maintained text now lives on [superlogical.com](https://www.superlogical.com/rex/docs/build/program-status). Its revision history lists 0.1 (2026-09-28), 0.2 (2026-10-06, "Clarify MUST NOT and apply keywords in more places"), and 0.3 (2026-10-07, "Absent progress means indeterminate. Programs may send reports without feature detection."). The gist was not updated past 0.1. Pi's issue and code link to the superlogical page, and Ghostty's PR links to the gist.

The stated motivation is that long-running terminal programs alternate between working, waiting on the user, and finishing, and that no existing sequence carries this state. According to the spec, OSC 9;4 can only say busy or not busy, notifications are one-off events, OSC 133 comes from the shell, and titles are unstructured. The blog post singles out "agentic inboxes" such as Herdr, cmux, and Agent Deck. It cites Herdr's regex rules over Claude Code's spinner title and their ten changes in three months as the heuristic approach that the protocol should replace. It also argues that out-of-band socket APIs do not cross SSH or container boundaries, whereas the pty does. The post says the work came out of Superlogical (the Rex terminal) and Ghostty, and that Hashimoto shared the draft with other terminal and application maintainers. The protocol is not registered with terminal-wg. A search found no freedesktop.org proposal, so that is unverified.

## The wire format is one OSC of colon-separated key=value pairs, with an echo-style support query

All of the following comes from the [current spec](https://www.superlogical.com/rex/docs/build/program-status), revision 0.3.

**Sequences.** A report is `ESC ] 7501 ; pairs ST`, and the support query is `ESC ] 7501 ; ? ST`. `ST` is either `ESC \` or `BEL`. The grammar is `pairs := pair (":" pair)*`, `pair := key "=" value`, `key := [a-z]+`, and `value := [A-Za-z0-9_.,+/=-]*`. Values cannot contain `:` or `;`, so nothing needs escaping. Whitespace around keys and values is removed. A malformed pair is skipped while the rest of the report still applies. Unknown keys MUST be ignored, which is how the protocol is extended. When a key repeats, the last value wins.

**Payload encoding.** `msg` and `title` are standard base64 of UTF-8 text, and padding is optional. If the decoded text contains a C0 control character, DEL, or a C1 control character, the whole report is discarded.

**Keys.**

| Key | Values | Notes |
| --- | --- | --- |
| `state` | `idle`, `working`, `done`, `blocked`, `error`, `clear` | Required. An unknown value discards the report. |
| `id` | `segment("/"segment)*`, segment `[A-Za-z0-9_.+-]{1,32}` | Absent means the root record. An invalid id discards the report. |
| `kind` | `permission`, `question`, `auth` | Read only with `blocked`. |
| `progress` | integer 0–100 | Read only with `working` or `blocked`. Absent means indeterminate. |
| `app` | `[A-Za-z0-9_.+-]{1,32}` | Inherited from the nearest ancestor record. |
| `title` | base64 UTF-8 | A short label. |
| `msg` | base64 UTF-8 | One line of text. Terminals MUST NOT parse meaning out of it. |

**Records.** A terminal, defined as one pty (a window, tab, split, or pane), holds one record per id. Each report replaces its record completely. `clear` removes the addressed record and its descendants, and `clear` with no `id` removes all records. When the pty's process exits or a new prompt starts (OSC 133 `A`), the terminal MUST drop `working` and `blocked` records and MAY drop `idle` ones. `done` and `error` records survive both events. RIS removes every record, while DECSTR and switching to the alternate screen do not. The protocol has no heartbeat.

**Query and capability detection.** A program sends `OSC 7501 ; ? ST`, and a supporting terminal MUST reply with the same body, `?`. Later revisions may append pairs after the `?`, and programs must ignore pairs they do not understand. The spec suggests sending DA1 (`CSI c`) right after the query: if the DA1 reply comes first, the protocol is unsupported. Since 0.3, detection is optional, because terminals must already ignore unknown OSCs. Terminals SHOULD add the terminfo string capability `Pst=\E]7501;%p1%s\E\\`. A program that does not find `Pst` must not conclude that the protocol is unsupported, because terminfo is unreliable over ssh and inside multiplexers. The query reply is authoritative.

**Security and limits.** All report content is untrusted. Text must not be treated as markup, and text shown outside the grid SHOULD have bidirectional overrides and invisible formatting characters disarmed. The fixed `?` reply is the only response a terminal ever writes, and there is no way to read records back. A displayed record SHOULD name the terminal it came from, so that one pane cannot impersonate another. Side effects such as notifications SHOULD be rate-limited. The hard caps are:

| Item | Cap |
| --- | --- |
| Whole sequence | 4096 bytes |
| Key | 16 bytes |
| `msg` | 2732 bytes encoded, 2048 bytes decoded |
| `title` | 256 bytes encoded, 192 bytes decoded |
| `app` | 32 bytes |
| `id` | 128 bytes, 32 bytes per segment, 8 levels |
| Records per terminal | 256, with a minimum of 64 required and least-recently-updated eviction |

A report that breaks any cap is discarded whole.

## Pi 1.1.0 emits root-record reports, gated on a query answered before DA1

Mario Zechner (`badlogic`) opened [earendil-works/pi#10607](https://github.com/earendil-works/pi/issues/10607) on 2026-10-07 with a mapping from pi states to reports. Pi reports `idle` at startup and on abort, and `working` during turns and compaction. Extension dialogs report `blocked:kind=question` or `blocked:kind=permission`, and the login dialog reports `blocked:kind=auth`. A settled run reports `done`, an error reports `error`, and quitting reports `clear`. Every report carries `app=pi`. The issue says that at the time only the Rex macOS beta displayed these reports, and that the Ghostty app ignored them.

The implementation is commit [`503c605`](https://github.com/earendil-works/pi/commit/503c605528f9af993c0e37ede468cf884fb0ff5b) (2026-10-07), released in tag `v1.1.0` and published to npm as `@earendil-works/pi-coding-agent@1.1.0` at 2026-10-07T22:16Z. See [packages/tui/CHANGELOG.md, line 30](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/tui/CHANGELOG.md?plain=1#L30). The locally installed pi is 1.0.4, and its package tree contains no `7501`.

- [packages/tui/src/program-status.ts, lines 19–53](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/tui/src/program-status.ts#L19-L53) defines `PROGRAM_STATUS_QUERY = "\x1b]7501;?\x1b\\"`. It matches the reply with `/^\x1b\]7501;\?[^\x07\x1b]*(?:\x07|\x1b\\)$/` and builds reports that contain only `state`, `app`, `kind`, and `msg`. It replaces control characters with spaces and truncates the message to 2048 UTF-8 bytes before base64-encoding it. Pi never sends `id`, `title`, or `progress`.
- [packages/tui/src/terminal.ts, lines 285–299](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/tui/src/terminal.ts#L285-L299) sends the kitty keyboard query, the 7501 query, and DA1 in one write. [Lines 239–243](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/tui/src/terminal.ts#L239-L243) mark the terminal as supported only if the reply arrives while the query is still pending, which means before DA1. [Lines 472–476](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/tui/src/terminal.ts#L472-L476) send `state=clear` on stop. `PI_PROGRAM_STATUS=1` forces reports on and `PI_PROGRAM_STATUS=0` turns them off.
- [packages/coding-agent/src/modes/interactive/program-status-reporter.ts](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/src/modes/interactive/program-status-reporter.ts) maps agent events to states. Its doc comment says prompts and model output are never reported.
- [packages/coding-agent/docs/terminal-setup.md, line 233](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/docs/terminal-setup.md?plain=1#L233) states that "tmux and screen do not forward them". That is pi's claim. This investigation did not check it against tmux source.

## Claude Code 2.1.295 emits root and child records, also gated on the query

The [Claude Code CHANGELOG at `602df92`, lines 3–6](https://github.com/anthropics/claude-code/blob/602df92bf481ed904533e95c09f740f40aab5aed/CHANGELOG.md?plain=1#L3-L6) lists under 2.1.295: "Added Program Status Protocol (OSC 7501) support: terminals that implement it can show whether Claude Code is working, waiting on you, or done". npm published 2.1.295 at 2026-10-08T18:22Z. The `@anthropic-ai/claude-code` tarball is now a native-binary wrapper, so the search covered the platform package `@anthropic-ai/claude-code-linux-x64@2.1.295`, file `package/claude`. Claude Code's source is not public. The following is read from minified identifiers and may change between builds:

- An OSC code table includes `PROGRAM_STATUS:7501` alongside `TAB_STATUS:21337`, which is iTerm2's own session-status sequence.
- The query is `gh(jp.PROGRAM_STATUS,"?")`, and it matches a reply whose data starts with `?`. The startup probe runs it together with XTVERSION and the kitty keyboard query. It records `"probe: OSC 7501 reply"` when the reply arrives, or `"probe: no reply to OSC 7501 ; ?"` when another sentinel answer arrives first.
- The report builder always writes `state=…` and `app=claude-code`, then optional `id`, `kind` (with `blocked` only), `progress` (with `working` or `blocked` only, clamped to 0–100), and base64 `title` (192-byte cap) and `msg` (2048-byte cap). There are separate builders for `state=clear` and `state=clear:id=…`.
- A React-style hook diffs a map that holds the root record (key `""`) plus child records. It writes only the records that changed and emits `clear:id=…` for removed ids. On unmount it writes a global `state=clear`. Reports are written only while the `programStatus` capability is answered as supported.
- The bundle contains `state:"blocked"` with each of `kind:"permission"`, `kind:"question"`, and `kind:"auth"`.

The exact mapping from Claude Code UI states to report states could not be recovered from the minified code. This investigation found no environment variable for turning Claude Code's reports on or off.

## Other emitters and terminals exist; tmux, kitty, WezTerm, iTerm2, and zellij show no support

- **Rex (Superlogical)** displays reports in its session picker and tab headers and raises a `terminal.program_status_changed` Lua event, according to the "In Rex" section of the [spec page](https://www.superlogical.com/rex/docs/build/program-status). Rex is closed source, so this is unverified beyond its documentation.
- **tuios**, a Go terminal multiplexer, implements the protocol per pane and as a client of its outer terminal ([docs/PROGRAM_STATUS.md at `bc35a35`, lines 200–221](https://github.com/Gaurav-Gosain/tuios/blob/bc35a3584241444966ecd2a584c7b33e7c53558d/docs/PROGRAM_STATUS.md?plain=1#L200-L221)). It never passes a pane's sequence through to the outer terminal. Instead, it queries the outer terminal itself and re-reports each pane as id `<session>/<pane>`, rate-limited to once every 250 ms and capped at 64 records. It sends `state=clear` for each of its records on detach. The doc says its pinned libghostty-vt predates #14560, so tuios parses OSC 7501 itself.
- **Bubble Tea** added `ProgramStatus` in commit [`41bc626`](https://github.com/charmbracelet/bubbletea/commit/41bc6265643a4709ad355581b01e6bb70b2ed8ea) (2026-10-08). `gh search code` also finds emitters in `charmbracelet/crush` and `tuist/tuist`. Their release versions were not checked.
- **Open requests without implementations** were found for neovim, cargo, tqdm, indicatif, ratatui, hugo, cmux, Microsoft's `intelligent-terminal`, and others (`gh search issues "OSC 7501"`).
- **No support found.** `gh search issues` and `gh search code` found nothing about OSC 7501 or the Program Status Protocol in `tmux/tmux`, `zellij-org/zellij`, `kovidgoyal/kitty`, `wezterm/wezterm`, `gnachman/iTerm2` (GitHub mirror), or `microsoft/terminal`. ## Kiwa's pinned ghostty-vt predates OSC 7501 and drops it silently

[build.zig.zon](../../build.zig.zon) pins Ghostty [`b094a6b`](https://github.com/ghostty-org/ghostty/commit/b094a6ba31825aec1b2beaae54686b4a31f98a8a), committed 2026-10-05. The GitHub compare API reports that the 7501 merge `a4aacd9` is 10 commits ahead of it. The vendored copy, `zig-pkg/ghostty-1.3.2-dev-5UdBC8jaeAW9dO18vmbJgR5b_ONbYu9dHyLPJiho6Srl/`, contains no `7501` or `program_status` anywhere under `src/`.

A pane writing `ESC ] 7501;… ST` takes this path through the vendored parser:

1. The parser's `@"7"` state accepts only `;`, `2`, or `7` next ([src/terminal/osc.zig, lines 974–979](https://github.com/ghostty-org/ghostty/blob/b094a6ba31825aec1b2beaae54686b4a31f98a8a/src/terminal/osc.zig#L974-L979)). The `5` byte calls `unknownOrInvalid`.
2. With `unknown_max_bytes == 0`, the default, `unknownOrInvalid` sets the state to `.invalid` ([lines 733–738](https://github.com/ghostty-org/ghostty/blob/b094a6ba31825aec1b2beaae54686b4a31f98a8a/src/terminal/osc.zig#L733-L738)).
3. `end` returns `null` for `.invalid` ([lines 1061–1072](https://github.com/ghostty-org/ghostty/blob/b094a6ba31825aec1b2beaae54686b4a31f98a8a/src/terminal/osc.zig#L1061-L1072)).

The vendored stream does have a generic hook for unknown sequences. It needs `Handler.unknown_sequence` plus a nonzero `osc_unknown_max_bytes` ([src/terminal/stream_terminal.zig, lines 103–142](https://github.com/ghostty-org/ghostty/blob/b094a6ba31825aec1b2beaae54686b4a31f98a8a/src/terminal/stream_terminal.zig#L103-L142); [src/terminal/stream.zig, lines 554 and 570](https://github.com/ghostty-org/ghostty/blob/b094a6ba31825aec1b2beaae54686b4a31f98a8a/src/terminal/stream.zig#L554-L570)). Kiwa sets neither.

Kiwa installs exactly five effects: `write_pty`, `device_attributes`, `bell`, `clipboard_write`, and `pwd_changed` ([src/pane.zig, lines 94–100](../../src/pane.zig#L94-L100)). OSC 52 writes are rebuilt and forwarded by `forwardClipboard` ([src/server.zig, lines 1308–1314](../../src/server.zig#L1308-L1314)). OSC 7 only updates the pane's directory ([src/pane.zig, lines 349–356](../../src/pane.zig#L349-L356)). The outer title is Kiwa's own `{hostname}: {workspace}` ([src/server.zig, lines 1663–1680](../../src/server.zig#L1663-L1680)), not the pane's title. OSC 133 and OSC 9;4 are not wired at all: no `semantic_prompt` or `progress_report` effect is set. Every other OSC, 7501 included, ends inside ghostty-vt. Nothing from a pane's OSC passes through to the outer terminal raw.

As a result, inside Kiwa today pi and Claude Code send `OSC 7501 ; ?`, get no reply, see DA1 answered first, and send no reports. This is the behavior the spec intends for a terminal without support. It also means that Kiwa never leaks a pane's records into the outer terminal.

## Supporting it means interpreting reports per pane; raw passthrough would break the spec

The spec defines "terminal" as one pty and puts record lifetime on that pty's process exit and OSC 133 prompts. Kiwa is the emulator for each pane's pty, so Kiwa is the "terminal" in the spec's sense. Raw passthrough to the outer terminal would be wrong for four reasons:

- Every pane's root record would collide in the outer terminal's single record set.
- The outer terminal never sees pane exits or pane prompts, so `working` and `blocked` records would never be dropped.
- A pane could clear another pane's records with `state=clear`.
- The query would be answered by the outer terminal for a pane that it does not emulate.

tuios rejects passthrough for the same reasons.

Kiwa has three options:

1. **Ignore it (the current state).** This is correct and costs nothing. Programs detect no support and stay silent. If a program skips detection, as revision 0.3 allows, ghostty-vt discards its reports.

2. **Interpret it per pane.** This option has five parts:
   - Bump the Ghostty pin to at least `a4aacd9`, which is a deliberate upgrade under ADR 0001 ([docs/adr/0001-zig-and-ghostty-vt.md](../adr/0001-zig-and-ghostty-vt.md)).
   - Set `handler.effects.program_status` in [src/pane.zig, lines 94–100](../../src/pane.zig#L94-L100). Setting it makes ghostty-vt answer the query through Kiwa's existing `writePty` ([lines 333–337](../../src/pane.zig#L333-L337)).
   - Keep up to 256 records per pane. Copy the decoded text, because report data is valid only during the callback.
   - Apply the lifetime rules. A pane's child exit drops `working` and `blocked` records. A new prompt does too, which needs a `semantic_prompt` effect to see OSC 133 `A`. For RIS, ghostty-vt already delivers the global clear before `reset`.
   - Show the records. The natural place is next to the activity marker (`Session.noteOutput`, [src/session.zig, lines 391–403](../../src/session.zig#L391-L403)), in the sidebar and tab row. The display must name the pane, strip bidirectional overrides, and rate-limit any notification.

   This fits ADR 0002, because reports are events and need no polling. It revisits the v1 decision to drop Herdr's agent-state icon because it needed heuristics ([.scratch/kiwa-v1/herdr-inventory.md, line 58](../../.scratch/kiwa-v1/herdr-inventory.md)). The glossary's activity-marker entry says _Avoid: agent state_ ([GLOSSARY.md](../../GLOSSARY.md)), so this work would need a new glossary term, for example "Program status".

   A pin bump is not strictly required. The vendored `unknown_sequence` hook with `osc_unknown_max_bytes = 4096` could catch `7501;` bodies. Kiwa would then have to reimplement the parsing, validation, caps, and `?` reply that upstream already provides.

3. **Interpret it and re-report to the outer terminal.** Under ADR 0004, the server owns the outer terminal, so the server would need to make three changes:
   - Add `\x1b]7501;?\x1b\\` before the DA1 in `probe_seq` ([src/server.zig, lines 66–69](../../src/server.zig#L66-L69)).
   - Teach the input decoder to recognize the reply. The decoder currently has no OSC branch: `parse` treats `ESC ]` as alt+`]` followed by plain keys ([src/input.zig, lines 301–319](../../src/input.zig#L301-L319)). It would need a `Reply` variant next to `device_attributes` ([lines 163–172](../../src/input.zig#L163-L172)), handled where probe replies are handled ([src/server.zig, lines 1370–1382](../../src/server.zig#L1370-L1382)).
   - Emit Kiwa's own reports with ids such as `<workspace>/<tab>/<pane>`, and send `state=clear` for each one before the server stops writing on detach.

   This option is useful only when Kiwa runs inside Rex or another consumer. It also needs the work from option 2.

Option 2 adds per-pane value whatever the outer terminal supports. Option 3 adds value only on top of option 2. The only Kiwa-independent consumers that exist today are Rex and tuios. Ghostty the app does not display reports yet.
